# 庭のキャンバス｜Garden Canvas

植えて、眺めて、入れ替えて。理想の庭を見つけよう。

公開URL: https://nature-wx-lab.github.io/garden-canvas/

## 正本と収録方針

本READMEが、Garden Canvasの目的・収録方針・実装上の判断・公開契約を所有する唯一の説明正本です。個々の植物の事実はデータファイル、実装はコード、特定リリースの確認結果は検証成果物が所有します。同じ植物台帳や進捗台帳を別の文書へ複製しません。実行版は `package.json`、カタログ版は `site/catalog.js` の `CATALOG_VERSION`、公開中の版は実際の配信ファイルとActionsを照合します。

- 対象は屋外の庭。庭木・宿根草・一年草・カラーリーフ・球根植物・バラ・クリスマスローズ・クレマチス・多肉・水生植物の10ジャンルを扱います。約3,000件は目安であり、件数合わせの架空品種・重複追加はしません。大きくなる桜・カツラ・クスノキ等も、成株寸法を隠さず含めます。
- 利用者提供資料は植物名だけを参照し、価格・説明・画像・その他の列を転用しません。室内観賞中心の植物は対象外です。白鳥（サボテン）、アデニウム・ブラック、寿光、ディソアンシーは除外指定を維持します。
- ドライガーデンは、関東など冬に霜が降りる平地での地植え越冬を基準にします。多肉・アガベという分類だけでは採用せず、種類ごとの耐寒性、排水、冬の雨などの条件を出典とともに扱います。全国一律の越冬保証ではありません。除外した旧カタログの保存個体は読込時に消しません。
- 人気順は店舗と掲載時点を区別します。園芸ネットの草花・庭木各300件と、おぎはら植物園の公開週間ランキングの収録情報を使い、現在の全国人気順位とは呼びません。バラは品種に加えて花色タイプでの収録も許容しますが、確認済みの花形・樹姿の違いは保持します。

現在のデータは2,946件です。これは収録数であり、写実的な年間再現の完成数ではありません。収録を変更したときは実データから再集計します。

## ツールの範囲

同じ庭を3Dで眺めながら、植物・季節・将来サイズ・購入予算・手入れを試す庭プランニングツールです。サーバーへの庭データ送信はありません。

- 実寸の外周（長方形・L字・自由多角形）、複数の花壇、多角形で近似する円形花壇、建物・通路・塀。幅・奥行き2〜30m、外周32頂点、花壇12区画、外構16個。外構は軸に沿う長方形です。
- 名前・別名・ジャンル・花色・樹形・資料・人気順・ドライガーデン条件で検索する植物カタログ。確認できた成株寸法、開花期、形態と出典を表示。葉形、枝、花穂・花房、落葉、冬の種子頭をコードで描き分けます。外観未対応や混合種は明示し、既知の種へ勝手に置き換えません。
- 個体ごとの追加・移動・複製・固定・削除・交換プレビュー。交換は採用／取消が可能です。案AからBを複製し、同じカメラ・月・経過年数で比較できます。最大100株／案、編集を40回まで戻す／やり直す。
- 季節と計画開始からの年数を別々に指定。個体の植える日、初期の高さ・株幅・葉高と、利用者が入力した将来の寸法を連動させます。草の株幅に応じて葉・茎の数も変わります。
- 剪定直後の寸法、自然な枝姿／外周を整える表現、回復月数を試せます。登録した剪定・切り戻しの月を予定表と3Dが共用。幹の構造を縮める目標は未対応として表示します。
- 新規購入株の入力単価を積み上げ、未入力数を併記。既存株・参考配置は除外します。初期サイズ変更時は価格と成長・剪定寸法を解除し、古い見積りを流用しません。
- 月別の手入れ、初年度のみの作業、所要時間の幅、水やり回数、月ごとに使える時間。準備・片付けは作業のある月に1回加算する利用者設定。時間超過でも作業は勝手に削除しません。
- 条件に合う植物候補から配置または交換を試せます。開花の参考、株幅の重なり、外周・外構への張り出しを表示します。美しさや栽培可否の採点ではありません。
- JSONで案・個体・予定・視点を保存・復元。0.1の保存ファイルも読めます。旧版の4形状は種類未指定のまま保持し、実在品種へ勝手に読み替えません。

## 見た目と動き

イロハモミジは専用の葉と枝構造を使用します。汎用の細長い葉から、7つの裂片が放射状に広がる掌状葉、細かな鋸歯、放射状の葉脈へ変更。葉柄で小枝につながる対の葉、横へ分かれる枝、葉群の間の隙間を描きます。[NC State Extensionの樹形・葉の資料](https://plants.ces.ncsu.edu/plants/acer-palmatum/)を形態の参考にしています。実木のスキャンや品種固有の精密モデルではありません。入力寸法を保つ専用の参考モデルで、年次成長の仮定は変更していません。

曲面の葉と花びら、細い枝・花茎、葉脈や樹皮の陰影、個体内の色の揺らぎを追加しました。風は株元を固定し、枝先のしなりと葉の細かな動きを組み合わせます。同じ変形を影にも適用します。芝・土は実素材の色と法線マップに小さな立体形状を重ねています。

風は「なし／そよ風／やや強め」、光は「日中／夕方」で切り替えられます。実際の風速・日照の計算ではありません。動きを減らす端末設定では風なしで開始し、非表示・画面外では描画を休止。通常最大30fps、40株超では最大24fpsとし、多数の植物は細部の密度を落とします。配置個体は省略しません。風と光は鑑賞用設定で、保存JSONの内容には含めません。

## 成長・手入れ・3Dの限界

**年次成長の予測、必要な剪定頻度、実写品質、外部AIアシストは完成していません。** 資料で確認できる成株寸法や「成株到達2〜5年」から、年ごとのサイズや管理回数を推定できるとは扱いません。

年次数値未設定の植物は初期サイズを保ちます。利用者が将来寸法と年数を入力した場合だけ、初期状態との間を直線補間し、設定年以降は固定する計画シナリオです。これは種別の生物学的成長曲線ではありません。別モードの「資料の成株上限」は資料の寸法上限を示し、指定年の予測や剪定後の姿と混ぜません。

剪定後の回復も入力した月数による直線的な仮定です。芽吹き・花芽形成・強剪定による樹勢低下・病害虫・根の競合・地域気候は計算していません。剪定予定が未登録なら寸法目標だけで剪定は起きません。予定表0件は手入れ不要を意味しません。実際に必要な作業の網羅性・頻度・所要時間は未検証です。

開花月・成株寸法は国内外の種苗元・販売元・植物園等の一次資料に基づく参考値です。資料の地域、露地・温室、品種・種の区別を保持します。日本の月を海外の月から機械的に決めず、地域差や資料間の違いを説明します。国内の対象品種の寸法を優先し、海外の種一般の値で上書きしません。「株幅40cm以上」のような下限だけの記載から上限を作らず、範囲を確定できない値は未確認のままにします。資料にない月境界・残葉率・寸法比は描画上の近似であり、各項目の未確認欄へ残します。

「高さ50cmまで」のように上限しかない場合も、50〜50cmの範囲や任意の下限を作りません。上限の原文を案内に残し、範囲を表す欄は未確認にします。「春〜秋」「初夏〜晩秋」の月への変換、切り戻しによる夏休み、無霜条件で冬まで続く開花は、品種固有の月別観測と区別します。管理例を全株に必須の無花月へ変えず、条件が異なる資料は条件と不一致を併記します。 数字で開始月だけが分かり終了が「秋の初め」等の場合も、全期間が月で明記された資料とは扱いません。季節を月へ換算した範囲は `bloomKnown:false` と画面の案内を一致させ、海外の換算月・国内の明記月を区別します。新しい資料を反映したら、古い「資料未照合」の説明が同じ植物の画面に残っていないかも確認します。

冬に地上部がなくなる宿根草、冬も葉を保つ種類、秋播き一年草、夏休眠する種類を分けます。落葉樹の冬枝は残し、草本の休眠では葉・花茎等の地上部を必要に応じて消します。一年草は開花後に終了し、翌秋に同じ個体が自動復活しません。再播種は別株として追加します。 保存個体の植える時期 `p.start` は0始まりの月インデックス（0＝1月、9＝10月）であり、秋植えは年をまたぐ存在期間と開花を確認します。内部の季節フラグだけで判断せず、個体の存在と実際の花の描画・接写可否を合わせて検査します。開花月が不明であることを「開花しない」「休眠する」と読み替えません。

冬の「落葉途中」と「地上部がなくなる」は区別します。見出しの常緑表記と低温管理下の苗の説明が異なる場合は、栽培条件を残して判断します。冬写真がないことだけで地上部や花茎を消さず、残存量が未確認ならその限界を明記します。月別の案内文と3Dは同じ根拠・地域条件に揃え、低温管理の参考姿を全国一律の状態として表示しません。

植物表現は手続き的な参考3Dです。葉の形・模様・裏面、枝の出方、幹と樹皮、花冠・花弁・萼・花序は種類別に実装を進めていますが、全株の健康な生育、花数、正確な枝ぶり、実写品質を保証しません。

### 完成の判定と資料の所有

`site/appearance-data.js` の `status` は `unconfirmed`（細部資料未確認）、`attributes`（資料属性を登録）、`partial`（個別の形態・季節を部分実装）の3段階です。`partial` は写実的再現の完成ではありません。全件分の記録があること、有限な形状を描けること、12か月のテストが通ることも、実物との一致を証明しません。実物同等と検証済みの件数は現時点で0件で、要求全体は未完了です。

植物ごとの出典URL・適用範囲（品種／種／属）・各形態の根拠・未確認事項を同じレコードへ置きます。資料写真は形態の観察に使い、転載許諾がない画像を公開資産へ複製しません。属の特徴や写真から置いた値を、品種の実測値へ格上げしません。品種名を同定できないものは候補を分け、断定しないで他の作業を進めます。

同じ販売ページの主写真・追加写真で花形や葉の出る季節が食い違う場合、商品名だけで既知の学名や形状へ結び付けません。現在の販売株との対応が確かめられなければ、裏付けのない学名・花・葉の割当てを撤回し、名称・確認済み寸法・出典と不一致を残す寸法枠に戻します。別種への再同定や単なる色変わりという説明で矛盾を埋めません。過去の販売ページは掲載年を明示し、現在の在庫や年間観察の証拠にはしません。

資料の構造化欄も本文・植物誌・写真と照合します。掌状脈を複葉と読み替えたり、突出する花柱を雄しべと決めたりしません。器官数などが食い違う場合は、採用した根拠と不一致を同じ植物レコードに残します。八重花の層数・分割数など、描画のための数値は実測の花弁数や器官同定と区別します。

同じURLの現在の学名が既存名と異なる場合、同じページ内で本文と構造化欄が食い違う場合、名称状態が未解決の場合も、その差を植物レコードに残します。同義語の確認は販売株・クローンの同一性の確認とは別です。品種の登録名と流通名を区別し、裏付けのない別品種への統合や個体IDの変更をしません。混植写真の別植物の花、写真URLのアップロード年月を対象植物の花期の根拠にしません。

キク科の頭花は舌状花、筒状花、総苞片を区別し、重なる舌状花の列数・枚数を写真1枚から品種の固定属性にしません。斑や単色の花を混ぜた表示も模様の例であり、発生率・温度変化の予測ではありません。葉の深裂や花弁の裏面色などは確認できた対象だけへ適用し、同じシリーズの別品種へ横展開しません。

「花径」が頭花・花房全体か、その中の小花かを区別します。ガーベラの舌状花・中間花・筒状花や、バーベナの中央のつぼみと周辺の開花を、一枚の花弁や一斉開花へ読み替えません。海外の育種名と国内の商品名の対応が未確認なら、特許の寸法は近縁の参考値として扱い、国内品種の実測へ格上げしません。若葉と成葉、匍匐枝の葉と花茎の葉は、資料が区別している場合に描き分けます。

外観の対応状況は `site/catalog.js` が組み立てた `CATALOG` と画面表示で集計します。元データの `visual` や `form` は `attachAppearance` で補われるため、元の値だけから未対応数の減少を報告しません。共通の参考形状から個別形状への改善と、未対応から参考表示への対応は別の進捗です。

判定には、出典の実物と全形・葉・枝・花を見比べること、冬・展葉期・開花期・花後の整合、月別モデルの検査、実際の公開画面の確認が必要です。モデル件数を増やすだけで完了扱いにせず、平板な葉、規則的すぎる枝、寸法比や密度の不自然さも残件にします。掲載写真が不足する月の姿は未検証のまま明示します。

交換は「最初から別種を植えた計画」の比較です。元個体の座標・植える日を保持し、新種の仮の初期寸法に戻し、旧種の価格・成長・管理設定を解除します。将来の特定日に旧株を抜き新株へ替える履歴、曲線の直接編集、区画の穴、一括移動、地図・写真の取込みは未実装です。

## 操作と保存

1. 「庭をつくる」で外周・寸法、花壇、外構を用意します。寸法変更では配置と外構の平面寸法も伸縮します。固定株があるときや外周から植物・区画がはみ出す変更は受け付けません。
2. 「植える」で植物を選び、庭をクリックします。初期サイズは仮の配置入力で、販売苗の規格ではありません。「眺める・選ぶ」で配置モードを終了します。
3. 植物をクリックまたは一覧から選び、寸法、価格、将来サイズ、手入れを調整して「反映」を押します。資料は各植物の欄にあります。
4. ドラッグで回転、ホイール／2本指で拡大・移動。「全体」「真上」「目線」「寄って見る」で視点を戻せます。左右矢印でも回転、Escapeで形の編集等を解除します。
5. Bに複製するとAを残して比較できます。個体交換もプレビューしてから採用します。案を切り替えても視点・季節・経過年数を保持します。
6. 「保存」で `garden-canvas-plan-v2.json` を端末へ書き出し、「開く」で復元します。画面を閉じる・再読込する前に保存してください。自動保存・クラウド保存はありません。

保存形式はversion 2、modelVersion `scenario-1`。catalogVersionは実装内の現行値を使い、既存の版から個体ID・案・利用者の入力を保って移行します。読込は3MBまで、個体・区画・作業件数、有限数値、範囲、未知項目、重複ID、外周内包含を検査します。不正なファイルは元の庭を保持したまま拒否します。手入れ予定は1株36件まで、表示年は0〜10年です。

## プライバシーと公開境界

庭は画面のメモリーだけに保持し、再読込するとサンプルへ戻ります。住所・位置情報・写真・ログインは取得しません。庭を共有URL、サーバー、アクセス解析、外部AIへ送る機能はありません。保存ファイルには庭の寸法・配置・価格・予定が含まれるため、利用者自身で管理してください。配信元GitHubには通常のHTTPアクセス情報が届きます。

描画ライブラリを同梱し、外部CDN・フォント・計測タグは読み込みません。Content Security Policyのmeta指定で外部通信、埋込み、フォーム送信等を制限します。GitHub Pagesではアプリが任意のHTTPセキュリティヘッダーを設定できず、metaはHTTPヘッダーの完全な代替ではありません。フレーム埋込み制限はこの配信方式では保証しません。秘密情報やクラウド保存の追加には別途設計が必要です。

専用の独立リポジトリを配信元とし、`scripts/release_check.py` の `SITE` に列挙した25ファイルだけをPages artifactに含めます。公開リポジトリの許可対象は `ALLOWED` の36ファイルです。これらと全到達可能コミットのファイル・氏名・メール・メッセージを同検査で確認します。許可外ファイル・個人メール形式・ローカルパス・主要な資格情報形式は配信を停止します。未知の秘密や全個人情報を静的検査で完全検出できるものではなく、差分の目視確認も必要です。

author・committerは `nature-wx-lab` と確認済みGitHub noreplyを使用し、個人のGit既定値を継承しません。Actionsは検査時に読み取り権限だけ、配信ジョブにPages用の権限だけを付与します。Actionsは固定commitを参照し、独自の長期認証情報は不要です。

## 開発と検証

```sh
python3 -m http.server 8765 --bind 127.0.0.1 --directory site
npm test
python3 scripts/release_check.py
```

変更はこの専用リポジトリで行い、許可ファイルだけを明示的にstageします。親ワークスペースや作業用フォルダをまとめてstageしません。公開更新の依頼を確認し、UI検証とリリース検査後にmainへpushするとActionsが検査・配信します。公開直前の検査には `--publish-request`、`--preview-verified`、`--target nature-wx-lab/garden-canvas` を渡します。検査中は対象の追跡ファイルを変更しません。

変更した形態・季節の代表例と境界例を先に検査し、CIで既存のモデル・カタログ・樹木・形態テストを実行します。検証範囲は変更に比例させ、過去の全画像・全データを理由なく作り直しません。個別植物の変更では対象IDの大小の寸法・12か月と直接影響する近縁形状を使い、寸法の有限性・器官の区別・季節境界・旧保存の互換を確認します。新しい形状名は描画側で対応していることを確かめ、データ項目と出典には許可スキーマ・範囲・参照先の検証を加えます。葉数・花器・月別状態のテストと、実物との視覚照合は別の工程です。

版を更新するときは `package.json`、HTMLとモジュール参照のキャッシュ用版番号、`CATALOG_VERSION`、旧カタログ版の読込とそのテストを揃えます。公開前検査は成功行だけでなくプロセスの終了コード0まで確認し、検査対象の変更後は古い合格を流用しません。

形状を共通モデルから専用モデルへ移すときは、新しい形状の検査に加え、既存の植物群を列挙する検査・花形の許可値・器官数も確認します。件数などの同じ文字列をファイル全体で置換せず、対象の検査名と周辺文脈を指定し、差分に他の植物群の変更が混ざっていないかを読む。CIが失敗した場合は失敗箇所を再現し、対象の検査とデータの不整合を直してから公開を再判定します。 専用テストだけでなく、変更した出典・根拠のスキーマと既存の共通契約を公開前の最小集合に含めます。`sources[].scope` は既存スキーマの分類値を使い、「国内品種」「品種試験」等の自由な説明を分類値として追加しません。資料の地域・試験条件は説明欄へ残します。旧契約が花形・葉の配置・冬姿を列挙する場合は、資料不足による割当て撤回や新しい器官を意味のある条件で検証し、許可値の無制限化・検査除外・skipで整合させません。

専用形状の共有レジストリには既存と衝突しないキーを使います。同じキーへ新形状を再登録すると、旧モデルの形状や意味を示すフラグまで上書きされるため、旧形状を残して新しいキーから呼びます。材質・共通処理を変える前後で、直接影響する代表個体の形状・インスタンス・色の配列を比較し、対象外の姿が変わっていないか確認します。観察位置だけを変える改修では乱数の消費順も保ち、花・葉の形状や色を変えていないことを同じ比較で確かめます。

対象ID・形状キー・部品名・葉の模様・季節状態を直接参照する既存テストを検索し、新しい専用テストと一緒に選択します。近縁植物を扱う別名のテストも対象です。旧名の互換を残すか同じ意味を検査する形へ整合し、空の部品や検査除外で合格させません。`leafPattern` の `center`・`margin` のような意味を持つ値を配色名へ変えず、配色は専用の値に分けます。月別の花色は `monthlyFlowerColors` を使い、未対応の単一項目を追加して表示に効いたと扱いません。花期未確認の形態レコードは `flowerMonths` を省略し、空配列で無花を断定しません。

独自形状では、葉の面の向き、花弁の面の向き、花筒の原点・長さを確認してから共通の座標変換へ組み込みます。葉柄・花茎・花筒が接続すること、大小の入力寸法で地面へ潜らないことを確認します。面の向きや単位長を推測した拡大縮小で合わせないでください。

表裏の色を分ける材質は実際の面の向きに対応させ、両面へ同じ裏色を塗りません。先端が二裂する面は裂け目だけでなく長軸方向の折返し・自己交差も確認します。花弁の鋸歯や切れ込みを輪郭へ置く場合、輪郭用の変数が内側の面まで繰り返し折り曲げていないか、同じ物理半径の断面でも確認します。形状・法線・インスタンス変換の有限性と寸法境界を保ち、保守的な外接箱が原因で疑わしい場合は変換後の実頂点で判定し、閾値を緩めて通しません。生成GLSLへ埋める数値は0も含め浮動小数表記へ揃え、GPUのコンパイルは実ブラウザのログで確認します。JavaScriptの単体テスト合格だけではGPUエラー不在を証明できません。

細葉の折れ・溝の深さは、正規化した座標だけでなく拡大後の実際の葉幅と比較します。長い葉の高さを掛けた凹凸が、細い葉を深い溝へ変えて斑を隠すことがあります。葉丈を高さと独立に小さくした入力も含め、変換後の葉が地面より上・入力した葉丈と株幅の内側にあることを確認します。寸法上限を直す場合、入力欄・保存JSONの一致だけでは適合の証拠にせず、インスタンス変換・株全体の変換・季節倍率を反映した実頂点で高さ、株元を中心とする水平半径の2倍、葉の最高点を判定します。対象の大小、適用可能な最小入力、開花・休眠、成長シナリオ・資料上限の代表例を選び、葉高だけの合格を株全体の高さ・幅の合格へ広げません。寸法へ収める変換と実物の形態との一致も別の検証です。CSS色の色相・彩度・明度を検査するときは、本実装の `Color.getHSL(target, SRGBColorSpace)` と線形色空間の値を混ぜません。

版の異なるローカル画像と公開画像の比較では、植物ID・入力寸法・月・選択個体・視点・風・光を揃え、不一致が植物本体か操作表示かを見分けます。

ローカル実装、ローカル確認、push、Actions配信、公開ファイル一致、公開画面確認を分けて報告します。公開ファイルは通常URLのbytesと配信対象commitの `git show <SHA>:site/...` を比べます。手元に次版の変更がある場合、作業ツリーのbytesで公開版を判定しません。PCとスマートフォンの代表操作・季節変化を確認し、表示崩れやコンソールエラーを記録します。

公開画像と元のローカル画像に差が出た場合は、まず入力・視点と配信対象を確認し、必要な対象だけを公開SHAの資産でローカル再現します。元画像との一致と、この対照再現との一致は別の件数として残します。版番号など操作表示だけの差を除く場合も、3D部分を無条件に除外せず、比較範囲と差を記録します。保存画像は拡張子に依存せず実形式・実画素数を読み、canvas領域の比較では保存画像とブラウザの内側寸法の比を使います。スクロールバーを除いたclient幅だけで切り出し座標を換算しません。 同じDOM寸法でも取得方法により保存画像の幅が変わった場合は、比較する両側で明示した同じ撮影範囲を使います。再取得する基準画像は凍結した同じコードを対象にし、元の比較と再取得による比較を区別します。canvas内の差と操作欄だけの差を実画像で確認し、画像幅の違いだけで接続障害やブラウザ設定を原因と断定しません。

複数の実装版をまとめて配信した場合も、実装時の版と実際に確認した配信版を分け、各対象の公開確認を記録します。一時fixture・ログ・適用済みの生成スクリプトは、今回の所有範囲と役割終了を確認して整理します。途中の表示修正を反映していない生成スクリプトを再実行したり、既存の作業フォルダを一括でstage・削除したりしません。 fixtureの回収前は、その回収単位の全ファイルを保存済み `fullDocument` と再照合し、現行検証を通してから所有する正確なファイルだけを削除します。公開待ちに必要な入力は保持し、所有不明の古いファイルには触れません。診断の入力・結果はPJ内の作業領域へ置き、利用者向けの「保存」を診断目的で押してDownloadsへ出力しません。表示する形態ラベルは日本語を確認し、内部の分類コードを説明の代わりに露出させません。

同じ形態・季節の処理を共有する品種では、品種ごとのPC成株・スマートフォン小株と、異なる季節挙動を代表する対象を選んで公開画面を確認します。共有処理の同じ季節を全品種で撮り直す必要はありません。実際に確認した対象・月・サイズと、その選定理由を各版の証拠に残します。調整前の画像を最終形状の合格証拠に流用せず、表示が疎ら、規則的すぎる、切れている等の問題があれば未完了として残します。資料カードの本文・花期注記はDOM内の存在だけで合格にせず、パネルをスクロールした後に表示枠内で読めることも確認します。

接写では、小さな葉に対して影の範囲と深度バイアスが大きすぎると、葉同士の影が消えて平板に見えます。風の頂点変形と深度描画は揃え、日中・夕方、樹木・草花・水面、近景・全体表示を必要な範囲で確認します。カメラや選択を変えた直後の古いフレームを新しい結果と誤認しないよう、選択状態を読んでから描画画像を確認します。

花の接写対象は、葉に隠れた軸や不可視の中心でなく、実際に描画した花序の表面に置きます。必要な植物群に限って距離と方向を調整し、中央の視線が目的の表面へ届くことを形状検査と画面で確認します。葉丈・株幅の変更や保存カメラの再読込でも確かめ、花期未確認・非開花・休眠中に架空の花の接写を用意しません。 CPUの視線検査は、交点をカメラ空間のnear/far範囲で絞ってから最初の可視面を判定します。クリップされる花弁への交差を、画面に見える根拠にしません。中央の狭い視線領域の合格を画面全体の花の被覆率へ言い換えず、小さな雄しべ等の影も実画面で確認します。見えにくい原因は形状の厚み・向き・密度・遮蔽とフレーム更新を切り分け、ブラウザの再起動や資料にない器官の拡大で埋めません。

長期作業は週の利用枠を節目で読み取り、その時点でユーザーが指定した残量以下になったら制作・公開を停止します。以前の0％・8％・15％・30％等を固定の基準として残さず、最新の指定を優先します。停止ラインに近づいたら、大きな作業単位へ入る前にも確認します。残量は他作業と共有され、確認間隔の間に変わるため、ちょうど指定値での停止やクレジット消費ゼロを保証しません。リセット権は使用しません。ユーザーが移行・一時停止を指定した場合は、制作を再開せず、移行先の初回依頼の範囲を守ります。
